# 0.58.0
## Breaking Changes
  - `PlatformEventType.SessionFilesAdded` (`session.files_added`) and `SessionFilesAddedPayload` are replaced by `PlatformEventType.SessionFileAdded` (`session.file_added`) and `SessionFileAddedPayload`. Adding several files to a session now publishes one event per file, the same grain as `file.uploaded`, instead of one event listing every file. Two things have to hold for a file to publish one. Its membership has to be new: re-declaring the time window or data range of a file already in the session changes no membership and publishes nothing. And its current version has to be `Available`: a file added while its upload is still in flight publishes nothing at that moment, and the upload's completion publishes it instead, so a compose-then-upload sequence still fires the trigger once the bytes are there. A file with no available current version at all — one being deleted, say — publishes nothing. The event is about the added file rather than the session: its payload names the session, the file's dataset, the file, and the file's version at publication; conditions and templates read `session.*`, `file.*` and `dataset.*`; and it fires once per occurrence, file or session. Both coarse grains collapse repeats — `once_per=session` dispatches for the first file added to a session and drops every later one, and `once_per=file` keys on the file alone, so adding the same file to a second session is dropped too — leaving `once_per=occurrence` as the grain that dispatches for every addition. An `InvokeActionTarget` on it takes the added file as the action's input, as it does for `file.uploaded`, so the target must carry at least one `required_inputs` pattern for the file to match; the grain that waives that rule is `once_per=dataset`, which `session.file_added` does not offer. An unqualified condition field binds to the dataset on the new event, where it bound to the session on the replaced one, so a condition written as `tags CONTAINS "x"` now reads the dataset's tags; qualify the field (`session.tags`) to keep the old reading. A trigger naming `session.files_added` no longer parses. Renaming the event is enough only where it was the trigger's sole subscription: a trigger subscribes to events about one kind of entity, and `session.file_added` is about a file where `session.created` and `session.updated` are about a session, so a subscription that paired the old event with either of those has to be split into one trigger per entity kind.
  - An `InvokeActionTarget` may no longer carry `required_inputs` or `additional_inputs` unless every event its trigger fires for exposes a `dataset` context, since those patterns match a dataset's files and there would be nothing for them to match. This is a wider refusal than the one it replaces, which rejected only `required_inputs`, and only on a scheduled trigger. It runs on create, on update and on enable, so an existing scheduled trigger that carries `additional_inputs` — legal to save until now, and ignored at dispatch — cannot be updated or re-enabled until that field is cleared; it keeps firing untouched in the meantime. Clear the field and select the invocation's inputs with `invocation_input` instead.
  - Experimental topic reads now raise `RobotoReadPlanExecutionException` for invalid timestamps, including rows previously skipped and timestamps previously wrapped to an incorrect value.

## Features Added
  - `curl -fsSL https://raw.githubusercontent.com/roboto-ai/roboto-python-sdk/main/install.sh | bash` installs the standalone CLI on macOS or Linux (`install.ps1` does the same on Windows) and runs the new `roboto setup`, which saves an access token and a default organization (`org_id` in the config file) and connects AI tools such as Claude Code and Cursor to Roboto's agent skills and MCP server. `roboto upgrade` updates the CLI and those skills.
  - `RobotoConfig.from_env` accepts an `env` argument, a `RobotoEnv` to read the access token, config file location, and profile from instead of the process's environment variables. `roboto.config.resolve_config_file(env)` returns the path of the config file the SDK reads: `ROBOTO_CONFIG_FILE` when set, otherwise `~/.roboto/config.json`.
  - `InvokeActionTarget` works on every platform event, not only file and dataset events, so save-time validation no longer turns it away from an event about a session, an invocation or an event annotation. With that, no target restricts what its trigger's events may be about, and the `subject_types` attribute the restriction was expressed through is removed from the target specs and from the target catalog. How the action gets its inputs turns on whether the event names a dataset, not on what kind of entity it is about. An event naming one — every file and dataset event, and `session.file_added` — invokes the action against that dataset, and what it hands the action as input depends on the trigger's grain. At `once_per=dataset` the dataset is the unit of work: the input is the files of that dataset matching `required_inputs`, plus `additional_inputs`. At every other grain on an event about a file (`file.uploaded`, `file.ingested`, `file.metadata_updated`, `session.file_added`) the file is the unit of work: the input is that one file's path, plus `additional_inputs`, and `required_inputs` decides only whether the target accepts the event at all — a file matching none of its patterns fires nothing, and a file matching one is the whole input whatever else the patterns would have matched. An event naming none — `session.created`, `session.updated`, `invocation.completed`, `invocation.failed`, `event.created`, and a schedule occurrence — has no dataset files to accept on or select from: the action is invoked with no data source and selects its inputs with `invocation_input`, whose string values may now contain `{{ }}` placeholders, for example `InvocationInput.from_session_id("{{session.session_id}}")`. A placeholder inside a selector's RoboQL `query` must sit inside a quoted value — `dataset_id = "{{dataset.dataset_id}}"` or `dataset_id = '{{dataset.dataset_id}}'`, not `dataset_id = {{dataset.dataset_id}}` — and a trigger that spells one anywhere else in a query, a comment included, is refused when it is saved. What the event resolves to is data, so it is escaped for the literal it lands in: a file path or tag containing a quote narrows the query rather than rewriting it, and one containing a newline, which no RoboQL literal can carry, fails that dispatch instead. The escaping keeps the value inside its literal rather than making it inert within one: a value reaching a `LIKE` pattern still matches `%` and `_` as wildcards, and a value spliced into a selector's `paths` is a glob pattern.
  - `FileUploadedPayload`, `FileIngestedPayload` and `FileMetadataUpdatedPayload` gain an optional `file_version`, the file's version when the event was published, which can be older than the file's current version by the time a trigger evaluates. Versions number revisions of the file record, so a metadata or tag edit advances one just as an overwrite of the file's contents does. The field is `None` on events published before the payload carried it. Conditions and templates read it as `envelope.data.file_version`: the `envelope` context now serves the platform event's payload, as published, under `data`.
  - `FilterOnlyComparator` gains `Last3Hours`, `Last8Hours` and `Last24Hours`, and `DateFilter` accepts them alongside the presets it already took. They are valueless like the rest: the comparator alone carries the range. Unlike `Today` and the day-based windows, which snap to a calendar boundary, these are measured back from the present, so they describe the same span of time wherever the reader is — a day-aligned window is a sliver of work for the hours after a UTC midnight that has not yet arrived locally. Nothing is removed: `Last90Days` and `ThisMonth` still parse and still resolve, so a filter saved with either keeps working.
  - `ClientViewingContext` gains `view_ids` and `table_state`, so a client can tell the agent about the resource table the user is looking at. `view_ids` lists the Views (saved searches) applied to that table, and `table_state` carries the table's `target` and its live `definition` in the same shape a View stores (RoboQL text or filter controls, plus visible columns, sort, and page size), whether or not a View is loaded. Both are informational, like the rest of the context: they let the agent resolve "this View" and "what I'm looking at" without the user spelling either out. `view_ids` defaults to an empty list and `table_state` to `None`, so existing callers are unaffected.
  - `CollectionRecord.resource_count` and `Collection.resource_count` report how many resources a collection holds. The service stores the count on the collection and keeps it current as members are added and removed, so it is present in every content mode, including `summary_only` loads where `resources` is empty. It counts every membership reference, including references to resources that have since been deleted, so a `full` load's hydrated `resources` map can hold fewer entries than the count says. `resource_count` is also a Collections query field: filter on it with the numeric comparators, or sort by it, through `RobotoSearch` and RoboQL.

## Bugs Fixed
  - Requests to the Roboto API, reads of files by URL, and the CLI's downloads check the server's certificate against the operating system's trusted roots, through `truststore`, a new dependency: Windows and macOS check it with their own certificate APIs, and Linux reads the system CA bundle. On a new Windows machine, these requests had failed with `CERTIFICATE_VERIFY_FAILED`: Windows adds most root certificates only when its own TLS code first needs one, and Python's check reads only the roots already there. When `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, Python's own check runs, as before.
  - The CLI now honors `ROBOTO_DEFAULT_HTTP_TIMEOUT`, and a config file profile's `default_http_timeout`: it gives up on a request that takes longer, and retries it when the request is safe to repeat, as the SDK does. With neither set, the CLI still waits for each request as long as it takes.
  - `ROBOTO_CACHE_DIR` and `ROBOTO_DEFAULT_HTTP_TIMEOUT` now apply when the access token comes from the config file, and override the profile's `cache_dir` and `default_http_timeout`. `RobotoConfig.from_env`, and the SDK and CLI clients built from it, had ignored `ROBOTO_DEFAULT_HTTP_TIMEOUT` in that case, and let a profile's `cache_dir` win over `ROBOTO_CACHE_DIR`.
  - The CLI's global `--config-file` option now takes effect. The CLI had read the file at `ROBOTO_CONFIG_FILE`, or the default one, whatever the option named.
  - `RobotoConfig.from_env` raises `ValueError` for a config file whose JSON isn't an object, as it does for any other unusable config file, instead of `AttributeError`.
  - `Condition.matches` always returned `False` for the `LIKE` and `NOT_LIKE` comparators, so a trigger conditioned on one never fired. They now match with SQL semantics: `%` is any run of characters, `_` is exactly one, a backslash makes the next character literal, and matching is case-sensitive over the whole value.
  - Creating or updating a View on `sessions`, `devices`, or `collections` with a RoboQL definition is now rejected with a 400. Those tables have no RoboQL mode, so such a View stored fine and then failed for whoever opened it. RoboQL Views on `datasets`, `files`, and `events` are unaffected; `roboto.domain.views.ROBOQL_VIEW_TARGETS` lists the supported targets.
  - Experimental topic reads select only the requested topic from multi-topic MCAP files, even when the topics have different schemas. They also handle nested Parquet timestamps and fields spread across files, with the same column order for split and unsplit partitions.
  - Experimental topic reads report read-plan failures as `RobotoReadPlanExecutionException` with a `kind`, including missing fields and partition schema mismatches.
