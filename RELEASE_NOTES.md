# 0.56.0
## Breaking Changes
  - `Metric.aggregate` (experimental) takes its new `group_by` between `condition` and `owner_org_id`, so the positional index of `owner_org_id` and `roboto_client` shifts by one. Both are keyword arguments in every documented use, and reaching them positionally means passing eleven or more positional arguments; a call that does breaks silently, binding an org ID to `group_by` and failing validation. Pass them by name.
  - Sessions, topics, and metrics (experimental): the `owner_org_id` parameter is removed from `Session.from_id`, `Session.for_dataset`, `Topic.from_id` (in `roboto.experimental.topics`), `TopicSchema.from_id`, and `Metric.get_by_session`. Each of these names a resource by a globally unique ID, and the service now checks access against the org that owns that resource, so the parameter no longer had any effect. Callers that passed it by keyword drop the argument; callers that passed the org positionally in the second slot now have `roboto_client` there instead.

## Features Added
  - `Metric.aggregate` (experimental) takes a `group_by`, splitting each period bucket by a field's value: one `NumericAggregateMetricRecord` per (period, distinct value) pair, each carrying the value it aggregated under the new `group_key`. Omitting it aggregates every matching data point of a period into one bucket, exactly as before, and the response for such a request is unchanged. Groupable fields are a deliberately narrow subset of the vocabulary `condition` accepts: `device.device_id`, and String, Enum, or Boolean custom fields on sessions and devices (`session.custom.<name>`, `device.custom.<name>`). Everything else returns HTTP 400 naming why it cannot be a group key — `collection.*` and the tag fields are set-valued, so a data point would be entered into several groups at once; `session.id` and `session.name` are unique per data point, so every group would hold one; `session.duration`, the session timestamps, and Number or Timestamp custom fields are continuous, so every distinct value would be its own group. A custom field that is not `Ready` is rejected the same way it is for a filter. Data points carrying no value for the field are grouped under a null `group_key` rather than dropped, so the sessions a field was never set on stay visible. The response is not capped: every distinct value with data in the window comes back, so a high-cardinality field returns proportionally many records.
  - `Dataset.get_topic_time_bounds()` and `Topic.get_time_bounds_by_association(association)` return the earliest `start_time` and latest `end_time` across a dataset's topics, or across the topics of one file or dataset association, as a `TopicTimeBounds` (`roboto.domain.topics`). Each is one request against a new aggregate endpoint — `GET /v1/datasets/<dataset_id>/topics/time-bounds` and `GET /v1/topics/association/<association>/time-bounds` — rather than a client-side fold over every page of topics, which on a dataset holding thousands of them took seconds. Both fields are `None` when the dataset or association has no topics, and either is `None` when no topic in the set carries that timestamp; a topic with no timestamps is skipped rather than pulling the answer to `None`. The topic set each aggregates is exactly the one the listing beside it returns: `Dataset.get_topic_time_bounds` covers what `Dataset.get_topics()` yields, and `Topic.get_time_bounds_by_association` what `Topic.get_by_file()` yields for a file association, current file version included. Authorization is unchanged from those listings — view access on the dataset, or on the file or dataset named by the association.
  - `ClientViewingContext` gains an optional `display_time_anchor_ns`: the epoch-nanosecond instant the client renders as t=0 when the user views timestamps relative to an anchor. Like the rest of the context, this field is informational. It lets the agent resolve a bare relative time the user types ("around 65 s") to an absolute instant, but the agent still writes absolute nanoseconds in its replies. Because a 19-digit integer does not survive a JavaScript number (and `JSON.stringify` refuses a `bigint`), a client may send the value as a decimal string; it is read as an `int`. Alongside it, `display_time_anchor_label` carries what the client shows the user as the name of that t=0 — "Start of workspace", or a picked timestamp rendered as local time — so the agent can name the instant an offset is counted from instead of leaving the reader to guess which one it meant. It is `None` whenever `display_time_anchor_ns` is.

## Bugs Fixed
  - `import roboto` failed on Python 3.10 with `AttributeError: module 'enum' has no attribute 'StrEnum'`, though the SDK supports 3.10 (`requires-python = ">=3.10,<4"`). Three enums in `roboto.query.filters` used `enum.StrEnum`, added in Python 3.11; they now use the SDK's Python 3.10 compatibility shim. Their values are unchanged.
  - A `sessions` input selector naming sessions by ID, and `Session.from_id` generally, work for a caller who belongs to more than one org without naming the session's org. The service now authorizes a session-by-ID request against the org that owns the session, where it previously rejected the request as missing an org; for an invocation, that rejection failed setup with exit code 64 before the action container started. The same change applies to every `/v1/sessions/id/...` route, to listing a session's metrics, and to the topic-identity, schema, timeline-source, and partition lookups by ID. A caller outside the owning org now receives 401 for one of these IDs where it previously received 404.
  - `Invocation.query` accepts `data_source_id` and `data_source_type` as condition fields, so you can filter invocations by the data source recorded against them. An invocation records one when whoever invoked it named a dataset; one launched from a file, topic, or session selector without an explicit dataset records `__UNSPECIFIED_DATA_SOURCE__` instead, and no dataset filter matches it. The invocations query API accepts both names, but `Invocation.query` validated each condition field against `InvocationRecord`, which nests the pair under `data_source`; either name raised `ValueError` before the request left the client. No other SDK route reached the filter, since invocations are not a query target for `RobotoSearch` or RoboQL, so the only way to it was to POST the query specification with `RobotoClient` and parse the returned records yourself. Code doing that can now call `Invocation.query` directly. Validation stays client-side: a condition naming a field the service does not accept still raises `ValueError` before any request is sent.
  - The `Invocation.query` docstring examples run as written. They previously called builder methods `QuerySpecification` does not have: `QuerySpecification().where(...).equals(...)`, `.order_by(...)`, and `.limit(...)`. Copying one raised `AttributeError` or `TypeError`. `QuerySpecification` is a plain model: conditions go in `condition`, ordering in `sort_by` and `sort_direction`, and paging in `limit`, which sets the page size rather than capping the result count. `max_results` does not bound this path either; `QuerySpecification` honors that field only for Roboto search targets. Bounding the number of results means slicing what `query` yields.
