# 0.64.0
## Features Added
  - Boards (experimental): a field control with a `topic` can name a field by its path, such as `{"path": ["gps.fix", "lat"]}` (`BoardTopicFieldPath`), so the control can offer a field when a name in its path contains a dot. A path can be the control's `default` or an option's `value`. A dotted name such as `"linear_acceleration.z"` still works.
  - `Topic.get_data`, `get_data_as_df` and `get_data_as_record_batches` in `roboto.experimental.topics`: the `RepresentationPreference` you pass as `prefer` takes `fallbacks`, selectors that a read tries in order when the representations that `default` selects cannot supply the fields you asked for. A read tries them separately for each partition (the part of a topic's data that one file holds). For example, `RepresentationPreference(default=RepresentationSelector(content_format="jpeg"), fallbacks=(RepresentationSelector(),))` reads a partition's JPEG when it has one and any other representation when it does not. With `default` alone, the read raises `RobotoInvalidRequestException`, before it returns any rows, when any partition has no JPEG. An override in `overrides` has no fallbacks: a read tries only the override's selector.
  - `SigV4AuthDecorator` accepts a botocore `Credentials` object, such as `RefreshableCredentials` for an assumed role, and reads it again for each request, so a long-lived process signing with an assumed role keeps working after the role's credentials expire. `ReadOnlyCredentials` are still used exactly as given.
  - RoboQL session filters (experimental): filter datasets, files and topics by `session.session_id`, `session.name`, `session.tags` or `session.custom.<name>`, and filter sessions by `topic.name` or `file.file_id`.
  - `QueryClient.get_query_results` accepts an optional `page_size`, the number of results per request, from 1 to `MAX_PAGE_SIZE` (1000, exported from `roboto.query`). A value outside that range raises `RobotoIllegalArgumentException` when iteration requests the first page. To cap the total number of results a query returns, set `QuerySpecification.max_results` or add `LIMIT N` to a RoboQL query.
  - RoboQL on `events` (experimental): filter on a session event's session (`session.name`, `session.tags`, `session.start_time`, `session.custom.<name>`), the session's devices (`device.device_id`) and its topics (`topics[0].topic_name`), and sort by `session_id`, `session.name` and `session.start_time`. These conditions never match dataset events.
  - To update a layout without overwriting someone else's changes, set `UpdateLayoutRequest.base_revision` to the `LayoutRecord.revision` of the layout you loaded. If anyone has updated the layout since you loaded it, `PUT /v1/layouts/id/<layout_id>` returns HTTP 409 and leaves the layout unchanged. A successful update returns the layout with its new `revision`; send that value as `base_revision` in your next update.
  - `RobotoSearch.find_collections` and RoboQL queries on `collections` can find the collections that hold a resource: `resource_id = "ds_..."` matches each collection that holds the file, dataset, event or session with that ID, and `resource_id != "ds_..."` matches the collections that do not hold it.
  - (experimental) `Agent.subject` says whether an agent runs on a dataset or a session (`AgentSubject`), or is `None`.
  - `InvocationRecord.resolved_input_data` and `Invocation.resolved_input_data` give the files, sessions and topics an invocation ran on as explicit IDs, whatever number of datasets they span. `InvocationRecord.input_data` is deprecated in favor of `rich_input_data`, which now holds the inputs as they were requested; a path selector in it that has no `dataset_id` is relative to the invocation's `data_source`.
  - `InvocationContext.get_input()` also reads an action's inputs when the platform passes the input manifest through the environment rather than as a file: as JSON in `ROBOTO_ACTION_INPUTS`, or, for a large selection, as a presigned URL in `ROBOTO_ACTION_INPUTS_URL`. `RobotoEnvKey` gains `ActionInputs`, `ActionInputsUrl`, and `StageInputs`; `StageInputs` says whether the invocation's selected files are downloaded into `$ROBOTO_INPUT_DIR`. `EgressPosture` can also be imported from `roboto`.
  - (experimental) `SessionCreateEventsGoal` has an agent create events on a session, named from its `event_vocabulary`. Import it from `roboto.ai.goals`.
  - RoboQL session queries can filter on `device.device_type_id`, for example `device.device_type_id = 'dt_…'`. `EQUALS` returns the sessions with at least one attached device of that type, and `NOT_EQUALS` returns every other session. `IS_NULL` returns the sessions none of whose devices has a type, including sessions with no devices, and `IS_NOT_NULL` returns the rest.

## Behavior Changes
  - `Topic.create` and `Topic.update` raise `RobotoInvalidRequestException` when the time range they would record for a topic ends before it starts, for example when a timestamp field's `Min` statistic is after its `Max`. They used to store the reversed range, which could give the topic, and any session that holds the topic's file, a wrong time span. `Topic.get_data`, `get_data_as_df` and `get_data_as_record_batches` in `roboto.experimental.topics` raise the same exception when a read covers a file that already has a reversed range; the exception's message names the file and says how to correct the range with `Topic.update`. Such a read used to return the file's rows or leave them out, depending on the time window you asked for. Older SDK releases get these errors too.
  - If you belong to more than one organization and call `POST /v1/ai/threads/<thread_id>/messages` directly, send the thread's organization ID in `X-Roboto-Org-Id`. A request whose `X-Roboto-Org-Id` names any organization other than the thread's now gets HTTP 400, and the error message includes the thread's organization ID. In SDK 0.63.0 and later, `AgentThread` and `roboto chat start` send the thread's organization ID for you.
  - Saving an agent is refused with `RobotoInvalidRequestException` when its goals mix dataset and session goals, or when a goal's `{{placeholder}}` names a variable of the wrong type. Existing agents are checked on their next update.
  - `CreateEventsGoal` is refused in organizations that create events only on sessions; use `SessionCreateEventsGoal`.

## Bugs Fixed
  - `Topic.get_data`, `get_data_as_df` and `get_data_as_record_batches` in `roboto.experimental.topics` no longer limit a read to the span between the first and last times recorded for the topic or the session when you omit `start_time` or `end_time`. A bound you omit sets no limit, so the read can return rows outside those recorded times; a bound you pass still applies. The fix applies to a topic of a session, file, dataset or device; a topic from `Event.get_topic` or `Event.get_topics` still defaults to the event's start and end. Reading a topic of a session that has no files returns no rows instead of raising `ValueError`.
  - `Topic.get_data`, `get_data_as_df` and `get_data_as_record_batches` in `roboto.experimental.topics` return the rest of a topic's data when one of the topic's partitions (the part of a topic's data that one file holds) has no stored data that the read can use, for example because the partition's stored data has fields outside the topic's schema. Before it returns the first row, the read issues one `UnreadableTopicPartitionsWarning` that names the partitions it leaves out. Such a read used to fail with HTTP 500. A read still raises `RobotoReadPlanExecutionException` when a partition can supply only some of the fields you asked for. In either case, an older SDK release gets a `RobotoDeprecatedException` that asks you to upgrade.
  - `Topic.create`, `Topic.update`, `Session.add_file`, `SessionFile`, `AnalysisScope` and declared timeline sources such as `McapLogTimeSource` keep a time in nanoseconds exact when you pass it as a NumPy integer, such as a value from a NumPy or pandas column. They used to round a present-day time to a multiple of 256 nanoseconds.
  - `Topic.get_data`, `get_data_as_df` and `get_data_as_record_batches` in `roboto.experimental.topics` no longer return a replaced file's old data from the local cache (see `CachePolicy`). A read fetches the version of each file that is current when the read starts. Renaming or moving a file, or editing its tags, metadata, description or device, also creates a new version of the file, so the next read downloads the file again.
  - `Topic.get_data` and `Topic.get_data_as_df` log a warning when `message_paths_include` or `message_paths_exclude` leave no message paths other than the timestamp. That warning previously never fired. They also log a warning naming each message path the topic's Parquet file has no column for, and read the rest, instead of leaving it out silently.
  - `Event.get_data` and `Event.get_data_as_df` load an event's data from the topic named by `topic_name` when the event's message paths are in more than one topic, or, for an event without message paths, when it was made on more than one topic. For message paths, they load only the event's message paths in that topic. They used to refuse such an event even when given `topic_name`. They still raise `RobotoInvalidRequestException` when `topic_name` is missing, names none of those topics, or names two that share the name, such as the same topic in two files.
  - `roboto actions init` checks for Git and Docker before it creates an action package, and no longer needs a Roboto access token or config file. Without Git, it exits with an error that links to Git's install page. Without Docker, it prints a warning that links to Docker's install page, then creates the package. When downloading the template or one of its Git steps fails, it exits with an error, not a Python traceback.
  - `roboto tokens --help` describes `list` as listing your access tokens. It used to describe `list` as creating a token.
  - `Dataset.put_tags`, `File.put_tags` and `Event.put_tags` say in their docstrings that the given tags are added to the existing tags. They used to say the given tags replaced the existing tags.
  - `Topic.get_data`'s sample record, in the Notes section of its docstring, renders as one code block. Only its opening brace used to render as code, and the rest as a nested list.
  - A device ID must not be empty, `.` or `..`, and must not contain a control character, such as a tab or newline, or any of `:`, `@`, `/`, `?`, `#` or `%`. The API accepted any device ID, but the web app could open the wrong page for a device with such an ID, links to the device could open a different device or none, and a device with `:` in its ID could not use its token to create or change data. Creating a device with such an ID now fails with a 400, and the SDK's `CreateDeviceRequest` raises `pydantic.ValidationError` before sending. Existing devices keep their IDs, and `Device.get_or_create` and `roboto devices register` still return them.
