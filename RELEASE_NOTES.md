# 0.63.0
## Breaking Changes
  - `Topic.create_from_df` and `roboto.formats.parquet.generate_message_path_requests` assign `array` to a `list`, `large_list` or `fixed_size_list` whose elements are `int8` or `uint8`, because such lists typically hold raw bytes (an image, a serialized blob) rather than a signal to plot. A `list` or `large_list` of 8-bit integers was previously `number_array`; a `fixed_size_list` of them was `unknown`. Files already added keep the type they were given; nothing is backfilled, so a topic that holds both older and newer files declares two types for the same message path.

## Features Added
  - Session events (experimental): `roboto.experimental.events.Event` marks a moment or span in a session, optionally about specific topics. Create them with `Session.create_event`, list them with `Session.list_events`, and run actions on `session_event.created`. Contact Roboto to enable them.
  - `Invocation.query` can find the invocations that ran on a session: filter on `input.session_id` equal to the session's ID.
  - `InvocationStatus.from_value` matches a status name in any case, such as `"failed"` or `"FAILED"`; it used to match only the exact name, such as `"Failed"`.
  - `CancelActiveInvocationsRequest.condition` limits a bulk cancel to the invocations that match it, such as those on one session.
  - `AgentToolResultContent.artifacts` lists the files an AI tool run produced, each an `AgentArtifactRecord` with its `name`, size in `bytes`, `content_type` and `status` (for example `uploaded`, or `too_large` for a file that was not kept). `GET /v1/ai/threads/<thread_id>/tool-use/<tool_use_id>/artifacts/<name>` returns an `AgentToolArtifactResponse` whose `url` downloads one of those files and expires within minutes. Only callers who can read the thread get one. Import both models from `roboto.ai.agent_thread`.
  - `AgentMessage.created_by` names the Roboto user who sent a user message, so in a thread shared with your organization you can tell which member asked what. It is `None` on assistant and Roboto messages, on messages an agent launch, trigger or Slack mention wrote, and on messages sent before Roboto recorded authors. A forked thread keeps the authors of the messages it copied. Roboto sets it from the caller and ignores any value you send.
  - `Metric.get_by_session` takes `name_prefix` and `exclude_name_prefix`, which return only the session's metrics whose name starts with the text you give, or leave them out. For example, `Metric.get_by_session(session_id, name_prefix="topic_stats.")` returns only the session's topic statistics. `Session.list_metrics` (experimental) takes the same two filters. Both return at most 10,000 metrics and give no sign when a session has more, so use the filters to read such a session's metrics in parts.
  - `Session.list_topics` (experimental) yields topics whose `record` is a `SessionTopicRecord`, which also carries the topic's schemas, the earliest and latest instant of its data in the session (`start_time_ns`, `end_time_ns`), how many of the session's files carry it, and its message count once Roboto has computed the session's topic statistics.
  - `Session.get_topic_stats` (experimental) returns one topic's statistics over the session's data, grouped by field, such as the min, max, mean and percentiles of each numeric field.
  - `Session.get_topic_stats_run` (experimental) returns a `SessionTopicStatsRun`: whether the latest run Roboto triggered to compute the session's topic statistics is `scheduled`, `running`, `finished` or `failed` (`not_run` when none was triggered), when Roboto last tried to start it, and its action invocation.
  - `Metric.prune_session` deletes a session's metrics whose names start with a prefix you give, that were published before a time you give, and that the calling action invocation did not write. An action that republishes a session's metrics calls it after publishing, with the time its run started, so that metrics the run no longer writes do not keep their old values. Only code running in an action invocation may call it.
  - Sessions (experimental) have AI summaries. `Session.generate_summary()` starts an AI agent that investigates the session and writes a summary, `Session.get_summary()` reads it (raising `RobotoNotFoundException` when the session has none), and `Session.set_summary(text)` replaces it with your own text. Generating and setting a summary need permission to manage sessions in the session's org; each generation is charged against the org's AI credits. The routes are `GET`, `POST` and `PUT /v1/sessions/id/<session_id>/summary`.
  - Two agent goals act on one session: `SessionSummaryAgentGoal(session_id=..., summary_format_spec_prompt=...)` summarizes a session and stores the summary `Session.get_summary()` returns, and `SessionTriageGoal(session_id=..., label_vocabulary={label: description, ...})` applies the labels that fit as session tags. Both need permission to manage sessions in the session's org. Their results are `SessionSummaryGoalResult` and `SessionTriageGoalResult`; import all four from `roboto.ai.goals`. The web app's agent editor cannot edit these goals yet, so create agents that use them with the SDK; saving such an agent in the editor keeps them.
  - `TemplateVariableType.SESSION_ID` declares an agent variable that takes a session ID. Launching the agent refuses an ID that names no session in the org. A trigger on `session.ingested` can pass `{{session.session_id}}` to it.
  - `Field.element_names` (experimental, `roboto.experimental.ingest`) names each element of a fixed-width numeric array field when you declare a session topic, for example `["shoulder_pan", ..., "gripper"]` for a `float32[6]` joint vector. Only a top-level field typed `number_array`, whose `data_type` ends in one `[N]` and whose elements are not one byte wide (`uint8`, `int8`, `uint8_t`, `int8_t`, `byte`, `char` or `octet`, in any letter case), may carry names: exactly N of them, each non-empty and unique, and the field must have no child fields. A declaration that breaks a rule raises `pydantic.ValidationError`, and the API answers it with 400 and stores nothing. `SchemaFieldRecord.element_names` returns the stored names. Names are part of schema identity, so the same array declared with and without names is two schemas; schemas without names keep their checksums. Declare names only on Roboto deployments running this release: an older deployment ignores them without an error.
  - Session topics (experimental, `roboto.experimental.topics`) read named arrays by name. In `Topic.get_data`, a named array's value is a `NamedArray`: a `tuple` with the `namedtuple` methods (`_fields`, `_asdict`, `_replace`) that still works by position, slice, length and iteration, and also takes an element by attribute (`a.main_gripper`) or by name (`a["main_gripper"]`, which works for any name). `fields_include` and `fields_exclude` can address one element as the array's path plus the element's name, for example `("action", "main_gripper")`. Including elements without the array reads only those elements, in element order, while including the array itself reads every element; an excluded element is dropped. In `get_data_as_record_batches` a named array keeps its stored type and lists its element names as JSON under the field metadata key `ELEMENT_NAMES_FIELD_METADATA_KEY`, and `get_data_as_df(flatten=True)` keeps the array column and adds one `<array>.<element>` column per element. A named array whose element count differs from the number of names raises `RobotoReadPlanExecutionException` with kind `element-count-mismatch`; a fixed-size list of the wrong width is refused before any row is read. Element addressing needs a Roboto deployment running this release; an older one refuses the address as an unknown field.
  - `Session.get_topic_stats` (experimental) returns each element of a named numeric array as its own entry, whose `path` is the array's path followed by the element's name, such as `("action", "main_gripper")`. Elements follow their array's path in declared order; entries for topics without named arrays are unchanged.
  - `MessagePath.array_length` reads the fixed length of an array message path from the trailing `[N]` of its `data_type` (`float64[7]`, `float[4]`, `fixed_size_list<element: double>[3]`), and is `None` for a variable-length, bounded, or multi-dimensional array and for a scalar.
  - `Topic.create_from_df` and `roboto.formats.parquet.generate_message_path_requests` assign `number_array` to a `fixed_size_list` of numbers, and `array` to a `fixed_size_list` of 8-bit integers or of any non-numeric type; previously every `fixed_size_list` was `unknown`. A `fixed_size_list` of structs gets a child message path per struct field, as a `list` of structs does. Files already added keep the type they were given; nothing is backfilled, so a topic that holds both older and newer files declares two types for the same message path.
  - `ViewDisplay.unsorted` records that a View shows its results with no sort at all, which a `None` `sort_by` cannot say: that still means the target's default sort. It defaults to `False`, so existing Views keep their default sort, and a display that sets it alongside `sort_by` is rejected with a 400. Older SDK releases ignore the field, so they read such a View as using the default sort, and an update they send with the definition clears it.
  - Every `StubRobotoClient.expect_*` method accepts `caller_org_id`. An expectation set with it matches only a request made with that `caller_org_id`. A request no expectation matches now fails with an error that shows its caller and owner orgs, and that error is no longer replaced by the pending-expectations error when the `with` block exits.

## Behavior Changes
  - From API version `2026-10-22`, `RobotoSearch.find_events` also returns session events (`roboto.experimental.events.Event`). Add `session_id IS_NULL` to get dataset events only.
  - Metrics dashboards, announced in 0.53.0, are now correctly marked as experimental: `DashboardRecord`, `DashboardAccessibility`, `CreateDashboardRequest` and `UpdateDashboardRequest` in `roboto.domain.dashboards`, `RobotoDashboardRevisionConflictException` and `RobotoBoardRevisionConflictException` may change or be removed without notice.

## Bugs Fixed
  - A trigger name may contain only letters, digits, underscores and hyphens. The API accepted any name that contained at least one such character, such as `my trigger/v2`, and the web app could not open, disable or delete a trigger named that way. Creating or renaming a trigger, including a scheduled trigger, with any other character now fails with a 400, and the SDK's request models raise `pydantic.ValidationError` before sending.
  - `ActionParameter.default` stores a default that is not a string as JSON, so a boolean `false` default is `"false"` rather than `"False"`, and a list or dict default is JSON rather than its Python form, such as `'["a", "b"]'` rather than `"['a', 'b']"`. Actions created or updated from now on receive the JSON spelling when an invocation uses the default. A default given as a string is kept as written, and actions saved before this release keep the defaults they were stored with until you update them.
  - `Metric.query` no longer fails with `RobotoResponseTooLargeException` (HTTP 507) when `max_results` data points would exceed the size of one API response. `POST /v1/metrics/query` now ends such a page early and returns a `next_token` for the rest, which `Metric.query` follows as before. If you read the endpoint's pages yourself, only an absent `next_token` means the results are complete: a page can hold fewer than `max_results` data points and still have more after it.
  - `Invocation.query` accepts a status name in any case, such as `"failed"`, as the value of a `last_status` condition. The API used to answer such a query with a 500. A value that is neither a whole number nor a status name, or a `Comparator.Like`, `NotLike`, `Contains`, `NotContains` or `BeginsWith` comparison on `last_status`, raises `RobotoIllegalArgumentException`. A fractional number such as `1.5` used to match nothing and now raises too.
  - Garbage collection eschews imported files in user-supplied buckets. Therefore, only objects uploaded through Roboto are deleted, in Roboto-managed and customer read/write buckets alike. Imports work from any registered bucket, read-only or read/write; the SDK docs used to say read-only only.
  - `Org.create(bind_email_domain=True)` creates the organization without binding your email domain when that domain is one no organization may bind, such as `gmail.com` or another public email provider's domain, and issues a `UserWarning`. The `email_domain_binding_outcome` field of the `POST /v1/orgs` response is `bound`, `deny_listed`, or null when the request did not ask to bind a domain.
  - A dataset summary whose generation cannot start, for example because you lack permission on the dataset, is marked failed, so `Dataset.generate_summary().await_completion()` raises `RobotoFailedToGenerateException` instead of waiting forever.
  - `roboto chat start` answers every message for a user who belongs to more than one organization. It used to exit on the second message with "User in multiple orgs must provide --org, or set an environment variable called 'ROBOTO_ORG_ID'.", whether the organization came from `--org`, `ROBOTO_ORG_ID` or the profile saved by `roboto setup`.
  - An `AgentThread` names the thread's organization on every request it makes about the thread, so `send`, `send_text`, `invoke_skill`, `submit_feedback`, `fork`, `set_visibility` and `set_pinned` work for a user who belongs to more than one organization. They used to raise `RobotoNoOrgProvidedException` for such a user.
  - `Trigger.platform_event_samples` and `roboto triggers sample` no longer fail with `pydantic.ValidationError` when Roboto returns a sample for an event type missing from the SDK's `PlatformEventType`, such as a type added after your SDK release. `Trigger.platform_event_samples` leaves that sample out and returns the rest, and `roboto triggers sample` prints the sample you ask for instead of failing for every event type. Upgrade the SDK to a release that includes the event type to see its sample.
