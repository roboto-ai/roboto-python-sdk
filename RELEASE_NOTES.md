# 0.59.0
## Breaking Changes
  - `File.dataset_id` raises `RobotoIllegalArgumentException` for a file associated with a device or with the org itself, naming the file, its association type and ID, and pointing at `File.association`. It had returned the association ID whatever its type, so a device ID could be read as a dataset ID. For a dataset file it is unchanged. `File.add_topic` on such a file raises the same exception, saying that only a dataset's files hold topics.

## Features Added
  - `AgentToolResultContent` (a member of the `AgentContent` union) gains `payload`: the text or JSON value the tool returned, independent of any model provider's wire format. Threads fetched over the API always carry it — new writes persist it, and for results written before the field existed the server synthesizes it from the stored provider envelope at read time (the API strips the provider-formatted `raw_response` from responses, as it always has). For code reading results outside the API path, `resolve_payload()` reads old and new rows uniformly: it prefers `payload` and otherwise reconstructs the equivalent value from `raw_response` where that field is populated (the reconstruction is also exposed as `roboto.ai.core.synthesize_tool_result_payload`, and understands both the provider `toolResult` envelope and the bare output dicts client-submitted results persisted). `raw_response` is unchanged but now documented as legacy; prefer `payload` / `resolve_payload()` in new code. The change is purely additive: no existing field changes shape, and older SDK releases reading threads written after this change ignore the new field, so no minimum SDK version is required.
  - The service now writes `AgentClientContextEntry` blocks (added in 0.58.0) on user messages, in place of the hidden ROBOTO-role message the viewing context used to be stored in. This release speaks API version `2026-09-30`; older SDK releases, which cannot parse the block, are pinned to earlier versions and receive threads with these blocks removed.
  - RoboQL gains a `summary` field on datasets that searches each dataset's AI-generated summary, so `RobotoSearch.find_datasets` can find datasets by what their summary says, alongside any other condition (e.g. `summary CONTAINS "over-temperature" AND created > "2026-09-01"`). Files, topics, and events reach their dataset's summary as `dataset.summary`. It takes `CONTAINS`, `NOT_CONTAINS`, `LIKE`, `NOT_LIKE`, `IS_NULL`, and `IS_NOT_NULL`; text comparisons are case-insensitive substring matches, not matches by meaning, so OR the phrasings a summary might use. Only completed summaries are searched: a dataset without one matches `IS_NULL` and no text comparison, so `NOT_CONTAINS` returns only datasets whose summary was written and lacks the text.
  - `DeviceRecord.universal_device_id` is a Roboto-assigned ID for a device, of the form `dv_...`, unique across all orgs and never changed. It sits alongside `device_id`, which keeps its meaning as the name you chose for the device, unique within its org. Every device has one, including devices registered before it existed; the field is `None` only against a Roboto deployment that predates it.
  - `AssociationType` gains `Device` and `Org`, with `Association.device(universal_device_id)` and `Association.org(org_id)` to build them, and `Association.from_id` recognizes the `dv_` and `og_` prefixes. A device association is keyed on the device's `universal_device_id`, not its `device_id`. `Association.is_device` and `Association.is_org` sit beside `is_dataset` and `is_topic`.
  - `FileSystem` is the files associated with one dataset, device, or org: `dataset.files`, `device.files`, and `org.files` each return one, and it carries `upload_file`, `upload_files`, `upload_directory`, `list_files`, `list_directories`, `get_file_by_path`, `download_files`, `delete_files`, `rename_file`, `create_directory`, and `rename_directory` with the signatures those methods have on `Dataset`. An org's files are organized under its datasets, its devices, and the org itself; `device.files` holds a device's own files, such as calibrations and part manifests, and `org.files` holds files that belong to the org as a whole, such as shared URDFs or runbooks. `Dataset`'s file methods are unchanged and delegate to `dataset.files`. `device.files` is keyed on the device's `universal_device_id` and raises `RobotoNotReadyException` for a device loaded from a deployment that predates that ID. `CreateDirectoryRequest`, `RenameDirectoryRequest`, and `QueryDatasetFilesRequest` are also importable from `roboto.domain.files`; their `roboto.domain.datasets` imports keep working.
  - `File.association` is the dataset, device, or org a file is associated with, typed, and is the accessor to use for any file. `File.download` and `File.rename_file` work for a file of any association, as does the bulk download behind `download_files`: download credentials are fetched by association, where they were fetched by dataset.
  - A file can be linked into another dataset, device, or org without being copied, so a URDF kept once in `org.files` can sit in every device's files. `FileSystem.create_link(target, relative_path)` puts a link at a path among the association's files, creating missing parent directories, and pins one version of its target: passing a `File` pins that file's version, and passing a file ID pins the target's current version. Later versions of the target leave the link where it was; creating the link again at the same path re-points it, as the link's next version, and returns the link unchanged when it already pins that version. A file or a directory at the path is a conflict, and so is uploading a file where a link sits. The target must be a file in the same org, not a link or a directory. A link is a file record of its own, with `fs_type` `FSType.Link`, a size of 0, and a `uri` of `roboto://file/<target_file_id>?v=<version>`; `File.is_link` and `FileRecord.is_link` tell one apart. `File.download`, `File.get_signed_url`, and an action's file input selected by ID fetch the pinned version of the target, with read credentials for the target's own dataset, device, or org. A link stores no object, so `FileRecord.bucket` and `FileRecord.key` raise `RobotoIllegalArgumentException` for one rather than read its `roboto://` pointer as a storage location. Deleting a link never deletes its target; deleting the target leaves its links pointing at nothing. `list_files` and `download_files`, which read the association's `/query` route, `File.query`, and org-wide file search do not return links yet, so `delete_files` leaves links in place and an action's file input selected by query, name, or dataset path never includes one. Collections and events do not take links yet: adding one reports it as a missing file. Reach a link by its path with `get_file_by_path` or by its ID with `File.from_id`; directory contents list links beside files.
  - `RobotoUri` carries an optional `version`, written as the URI's `v` query parameter beside `t` and named by `roboto.uri.VERSION_QUERY_PARAM`. `RobotoUri.parse` reads it, and rejects a `v` that is not a whole number; a version below 1 is rejected at construction.
  - `FileTag.AssociationId` is the S3 object tag key that holds the ID of the dataset, device, or org a file is associated with. `FileTag.DatasetId` is deprecated in its favour: it names only a dataset, and a file's association may be a device or the org itself. The member stays, since the platform still tags its own server-side copies of dataset files with it.
  - `Device.delete` deletes the device's own files (`device.files`), every version of each, shortly after the device is gone. `Device.delete(keep_files=True)` moves them to the org root instead, under `devices/<universal_device_id>/` in `org.files`, keeping each file's ID and every version, so anything that refers to a file by ID keeps working; it requires permission to upload files to the org. Links among the device's files are deleted in both modes, never moved, and their targets are left alone. `roboto devices delete` gains `--keep-files` for the same.

## Bugs Fixed
  - `download_files` on `Dataset` and `FileSystem` raises `RobotoIllegalArgumentException`, naming the path, before downloading anything when a selected file's path would resolve outside `out_path`. It had written such a file wherever its path led. Action input preparation refuses such a path the same way.
  - `AgentThread.refresh()` and `run()` no longer splice a regenerated assistant reply onto the text of an attempt that was abandoned. A turn that hands off near its execution deadline leaves a partial reply behind; the continuation discards it and rewrites the reply at the same position, and a client that had already read part of the discarded attempt previously kept its text and appended only the tail of the real one. Threads read through `AgentThread` now resynchronize instead. `AgentThreadDelta` gains `reset_from_message_sequence_num` to carry that signal — it is `None` on ordinary deltas, and clients written against the SDK need no change. A client pinned to an older `roboto` release does not fail, since the field is optional and goes unread, but it now does worse than before after a reclaim: the server rewinds its position to the start of the regenerated message, so the older client appends the whole regenerated reply, not just its tail, to the discarded text it already held. Upgrade `roboto` to avoid this.
  - `roboto devices register` and `roboto devices generate-creds` work again. Since 0.58.0 both exited with "No Roboto config file found at specified path 'config.json'", because the CLI read their `-f/--config-file`, the path to write the device's new credentials to, as the location of the caller's own config file.
