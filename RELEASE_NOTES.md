# 0.61.0
## Breaking Changes
  - `roboto.waiters.TimeoutError` subclasses the built-in `TimeoutError`, which is an `OSError`, so an `except TimeoutError` or `except OSError` around a wait (anything that waits with `roboto.waiters.wait_for`, such as `Session.wait_until_ingested`) now catches it; `except roboto.waiters.TimeoutError` still works. Its constructor takes only the message, and no longer accepts arguments after it. `str(error)` is the message it was raised with, where it had been empty.
  - Since 0.59.0, `File.dataset_id` raises `RobotoIllegalArgumentException` for a file associated with a topic, as it does for a file associated with a device or with the org itself; the 0.59.0 notes named only devices and the org. Before 0.59.0 it returned the topic's ID. Use `File.association` for such a file.
  - Links can be created only in a device's or a device type's configurations or the org's assets: `create_link` on a dataset raises `RobotoInvalidRequestException`. 0.59.0 and 0.60.0 accepted a dataset. `delete_files` on a device or org now deletes the links it matches, leaving the files they point at; it used to leave links in place.
  - `Device.files` is renamed `Device.configurations`, and `Org.files` is renamed `Org.assets`. `Dataset.files` keeps its name, and each of the three returns a `FileSystem`. A device's configurations hold files specific to the device, such as URDFs, calibration files, manifests, and maintenance logs; recorded data goes to datasets. The `keep_files` argument of `Device.delete` is renamed `keep_configurations`, the `--keep-files` flag of `roboto devices delete` is renamed `--keep-configurations`, and the `keep_files` query parameter of `DELETE /v1/devices/id/<device_id>` is renamed `keep_configurations`. The old names are removed without a deprecated alias.

## Features Added
  - Sessions can be marked complete (experimental): a session is in progress or complete (`SessionRecord.status`, a `SessionStatus`), and `Session.complete()` declares that all of a session's files have been added. Once it is complete, the `session.ingested` platform event (`PlatformEventType.SessionIngested`, payload `SessionIngestedPayload`) fires as soon as every ingestable file in the session is ingested; a file is ingestable when its path matched one of the org's ingestion rules when its current version was created or it was last renamed or moved, or it has since been partly or fully ingested, and files that are not ingestable never delay it. Adding a file to a complete session puts it back in progress, and marking it complete again announces it again. If its ingestable files change while it stays complete (a file uploaded again, removed or deleted), `session.ingested` fires again once they are all ingested; editing a file's tags or metadata does not count as a change, and an announcement whose publish fails is sent again later; each announcement is a new occurrence numbered by the payload's `ingestion_number`. `Session.ingestion_status()` returns a `SessionIngestionStatus`: the state (`in_progress`, `processing` or `ingested`), how many ingestable files are ingested and not yet ingested (`ingested_file_count`, `pending_file_count`), how many of the files not yet ingested failed to ingest (`failed_file_count`), how many files are not ingestable (`not_ingestable_file_count`), up to 100 of the files not ingested yet (`pending_files`, each with when its current version was uploaded and its latest ingestion run, `last_run`), and the files the session no longer waits for (`skipped_files`). `Session.skip_waiting_for(file_ids)` stops a session waiting for files whose ingestion will not finish, such as failed ones; uploading a skipped file again makes the session wait for it again, while editing its tags or metadata does not. It returns a `SkipWaitingResponse`: the session's `SessionIngestionStatus` afterwards, and the requested files that are not in the session (`not_in_session`), which are not skipped. `Session.wait_until_ingested()` blocks until the session is ingested and the announcement is recorded (its `ingestion_count` has gone up); see the next entry for sessions in progress. Its default `timeout` of 10 minutes may be too short for large recordings, and on timeout its error says where the session stands and names up to 10 of the files it is still waiting for. An upload that has kept a file of a complete session reserved (started but not finished) for 24 hours is aborted, so the session is not held forever by an upload that will never finish. The first time a session in an org is marked complete, by a user or by its completion policy, Roboto installs a trigger named `roboto-session-metrics` in the org. It runs the `session_metrics` action (owned by `roboto-public`) on each session each time the session is announced ingested. Its `TriggerRecord.managed_by` is `ManagedBy(kind=ManagedByKind.System, id="session_metrics")`: org members may disable it, and it stays disabled, but they cannot edit or delete it. `Session.ingestion_summaries(session_ids)` (`POST /v1/sessions/ingestion/summaries`, 100 sessions per request) returns a `SessionIngestionSummary` per session: its state and file counts, including how many waiting files failed to ingest (`failed_file_count`), without listing files. `SessionRecord` gains `status`, `completed_at`, `completed_by`, `ingestion_count` and `ingested_at`. `completed_at` and `completed_by` say when and by whom the session was last marked complete, and a session put back in progress keeps them, so use `status` to tell whether a session is complete now. RoboQL session queries can filter on `status` (`in_progress` or `complete`), `completed_at`, `ingested_at` and `completion_policy` (`IS_NULL` / `IS_NOT_NULL`), e.g. `status = 'complete' AND ingested_at IS_NULL` to find complete sessions never fully ingested.
  - Sessions can complete themselves (experimental): a session created with a `CompletionPolicy` (e.g. `Session.create(..., completion_policy=CompletionPolicy(inactivity_minutes=15))`) is marked complete by Roboto once that long has passed since a file was last added to it. A session created without one gets the org's default completion policy, which org admins set in the web UI, and `SessionRecord.completion_policy` shows the policy applied; pass `completion_policy=None` to opt out. `SessionRecord` gains `completion_policy` and `completes_at`. `Session.update(completion_policy=...)` (`SessionUpdate.completion_policy`) sets or removes a session's policy later: on a session in progress that has files, a new policy counts its inactivity from now, and removing it means Roboto will not mark the session complete. A complete session stays complete and keeps the policy for after a file is added to it. `Session.wait_until_ingested()` waits through a session in progress that has a completion policy and files, since it will complete itself, and raises `RuntimeError` at once for a session in progress without a policy or without files. `Session.create_if_not_exists(match_roboql_query, ...)` returns the first session matching a RoboQL query or creates one, and concurrent calls with the same query create one session between them. A matching session is returned as it is, which may be complete: the arguments that describe the session to create, `completion_policy` among them, are ignored. The session created must match the query, or every later call creates another.
  - Ingestion rules (experimental): an org's ingestion rules decide which uploaded files are ingestable and how they are ingested. A rule has path patterns (`include_patterns`, `exclude_patterns`) and the action that ingests matching files (`invocation`); a dataset file whose path a rule matches when it is uploaded is ingestable (rules do not apply to files associated with a device or the org itself), and while the rule's `auto_ingest` is on, a trigger the rule owns runs that action on it. Turning `auto_ingest` off disables that trigger rather than deleting it, so its run history stays. The API is `/v1/ingestion-rules` (list, get, create, update, delete, `POST /match` to test paths, and `GET /defaults` for the rules Roboto offers to start from, each with a `category` to group it under, `for_new_orgs` saying whether sign-up offers it and `POST /defaults` creates it (ROS 1 bags, ROS 2 bags, MCAP files and PX4 ULog files), and `needs_settings` saying whether its action likely needs settings such as the timestamp column (CSV files and Parquet files); ArduPilot logs, CSV files and Parquet files are only offered as starting points). The SDK has the request and response models in `roboto.experimental.ingestion_rules` (`IngestionRuleRecord`, `CreateIngestionRuleRequest`, `UpdateIngestionRuleRequest` and others) but no client class yet: call the endpoints with `RobotoClient`, e.g. `RobotoClient.defaulted().get("v1/ingestion-rules")`. Creating, updating (including turning `auto_ingest` on or off) and deleting rules, `POST /v1/ingestion-rules/defaults` and `POST /v1/ingestion-rules/<rule_id>/existing-files/ingest` are for org admins only and return 401 to other members; reading rules stays open to every member.
  - Ingesting files that are already uploaded (experimental): `POST /v1/ingestion-rules/ingest` (`IngestFilesRequest`, up to 100 file IDs) marks each file ingestable and runs its matching rule's trigger on it, as if it had just been uploaded. Use it for a file uploaded before a rule matched it, or to run a failed ingestion again. It needs permission to edit each file, and reports what happened to each one (`IngestFileResult`, with an `IngestFileOutcome` such as `started`, `already_running` or `no_matching_rule`). `POST /v1/ingestion-rules/runs/latest` (`LatestIngestionRunsRequest`, up to 200 file IDs) returns each file's latest ingestion run, leaving out files the caller may not view, an `IngestionRun` saying whether it is `running`, `failed` or `finished` and which invocation it started. `GET /v1/ingestion-rules/<rule_id>/existing-files` returns an `ExistingFilesPreview` of the files already uploaded that the rule matches but never ingested, with sample paths only for org admins (the files may sit in datasets a member cannot open), and `POST /v1/ingestion-rules/<rule_id>/existing-files/ingest` (org admins, and only while the rule's `auto_ingest` is on) starts an ingestion run for each of them in the background. Those runs wait in the org's action queue like any other invocations, so uploads made meanwhile may wait behind them. The preview counts files uploaded before the rule existed and files uploaded while its auto-ingest was off, and how many complete sessions hold them (`complete_session_count`): each of those is announced fully ingested again once its files are ingested. Runs belong to a file's current upload: editing a file's tags or metadata keeps its latest run, while uploading it again clears the run until the file is ingested again, so the backfill includes it.
  - `FileRecord.ingestable` says whether a file is meant to be ingested: its path matched one of its org's ingestion rules when this version was created or when the file was last renamed or moved (a move decides again at the new path for a file not yet ingested), or it has since been partly or fully ingested. RoboQL file queries can filter on it, e.g. `ingestable = true AND ingestion_status = 'not_ingested'`.
  - `ClientViewingContext.session_ids` names the sessions the user is viewing when they send a chat message, so the AI can resolve "this session".
  - `ClientViewingContext.device_type_ids` names the device types the user is viewing when they send a chat message, so the AI can resolve "this device type".
  - `TriggerRecord.managed_by` (a `ManagedBy`, with `kind` a `ManagedByKind` and an `id`) names what owns a trigger that org members do not define: `System` for one Roboto installs for a platform feature, `IngestionRule` for the trigger an ingestion rule ingests files with. Neither can be edited or deleted through the triggers API. An ingestion rule's trigger names no file patterns, so it has no legacy shape: `roboto.domain.triggers.Trigger` lists and reads it, the legacy `roboto.Trigger` does not. A system trigger can be enabled and disabled; a rule's trigger cannot be changed at all except through its rule. It is `None` for every other trigger.
  - Saved filters' `StringFilter`, `NumericFilter`, `MetricFilter`, `EnumFilter` and `BooleanFilter` gain `or_null`, which allows an `EQUALS` / `NOT_EQUALS` row to match records where the field is not set ("a, b, or not set", "neither a nor b, or not set"). This release speaks API version `2026-10-06`; older SDK releases, which cannot parse such a row, never receive a View that uses one: View listings leave it out, and reading or updating it by ID asks the caller to upgrade.
  - `list_files` on a device, a device type or the org (`FileSystem.list_files`) returns links as well as files, with `File.is_link` set. `File.query` and org-wide file search return files alone, so a file linked from many places is one result, not many. `download_files` downloads each link to its own path with the contents of the file version it points at.
  - `FileSystem.delete_directories` deletes directories, with everything beneath them, from the files of a dataset, device, device type, or org. `DeleteDirectoriesRequest` moves to `roboto.domain.files` and is still importable from `roboto.domain.datasets`. For a device's, device type's, or org's files it is available only to organizations for which Roboto has enabled files on those.
  - Device types: a `DeviceType` is a named kind of device within an org, such as one robot model, with a `description`, `metadata`, and `tags` of its own. `DeviceType.create`, `from_id`, `for_org`, `update`, and `delete` manage one; `delete` raises `RobotoConflictException` while any device has the type, and otherwise deletes the type's configurations with it. `DeviceType.devices()` lists the devices of a type. A device has at most one type: `Device.create` takes `device_type_id`, `Device.set_device_type` assigns a type or, given `None`, removes it, and `DeviceRecord.device_type_id` and `Device.device_type_id` read it back. Device types are available only to organizations for which Roboto has enabled them, and are refused for other organizations.
  - Device type configurations: `DeviceType.configurations` is the type's own `FileSystem`, for files such as a URDF or a bill of materials that every device of the type shares, under a new association type: `AssociationType.DeviceType`, built with `Association.device_type(device_type_id)`, recognized by `Association.from_id` from its `dt_` prefix, and tested with `Association.is_device_type`. `RobotoUriType` gains `DeviceType`. `list_files` and `download_files` on a device's configurations (`device.configurations`) take `include_inherited=True` to include the configurations of the device's type as well; where the device and its type both have a file at the same path only the device's is included, and `file.association.is_device_type` tells which files came from the type. Nothing is copied: a file added to a type reaches every device of that type at once, and changing or removing a device's type changes which files `include_inherited` adds. `include_inherited` is refused for anything but a device's configurations, and the other `FileSystem` methods (`get_file_by_path`, `rename_file`, `delete_files`) act on the device's own configurations only.
  - The CLI gains `roboto device-types` (`create`, `show`, `list`, `update`, `delete`, `devices`), `--device-type-id` on `roboto devices register`, and `roboto devices update --device-type-id`, which takes `null` to remove a device's type.

## Bugs Fixed
  - `Dataset.create_if_not_exists` creates one dataset between concurrent calls with the same `match_roboql_query` in an org. Concurrent callers, such as workers handling one file each, could each find no match and each create a dataset. The service now runs such calls one at a time from the search through the create, and a call that waits more than 10 seconds for its turn fails with `RobotoServiceUnavailableException`, after the SDK's own retries; calling again is safe.
  - Fixed a bug in dataset file downloads introduced in SDK 0.59.0: against a Roboto deployment released before SDK 0.59.0, downloading, listing, and deleting a dataset's files and creating and renaming its directories failed. Device and org files require a Roboto deployment released with SDK 0.59.0 or later.

  - `Invocation.input_data` returns `None` for an invocation that specifies a dataset without selecting inputs. Reading it raised a pydantic `ValidationError`, "At least one file selector field must be provided!". `Action.invoke(input_data=[])` behaves like `input_data=None`: it selects no inputs and sends `data_source_id`, `data_source_type`, and `upload_destination` as given. It raised the same `ValidationError` when `data_source_id` was set, and `RobotoIllegalArgumentException` when it was not.
