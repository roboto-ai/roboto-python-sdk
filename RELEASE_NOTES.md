# 0.65.0
## Breaking Changes
  - Only a Roboto admin can change an organization's `status`. `Org.update` raises `RobotoInvalidRequestException` when anyone else tries to change it.
  - `Org.bind_email_domain` and `roboto orgs bind-email-domain` require an admin of the organization; other members get `RobotoUnauthorizedException`.
  - `Org.remove_user`, `roboto orgs remove-user`, and `DELETE /v1/orgs/id/<org_id>/users/id/<user_id>` succeed and change nothing when the user isn't a member of the organization. They used to fail in that case: `Org.remove_user` raised `RobotoNotFoundException`, the endpoint returned 404, and the command exited with an error. Code that catches that exception, or a script that checks the command's exit code, now sees success.
  - When another organization already holds your email domain, `Org.create(bind_email_domain=True)` creates the organization without binding the domain and issues a `UserWarning`; it used to raise `RobotoConflictException` and create no organization. Code that catches that exception should check for the warning instead.
  - Where your Roboto deployment requires verified email domains, `Org.bind_email_domain` and `roboto orgs bind-email-domain` start a verification of the domain instead of binding it. The command prints the DNS TXT record to publish; in Python, call `Org.start_email_domain_verification` instead of `Org.bind_email_domain` to get the record.
  - `Org.unbind_email_domain` and `roboto orgs unbind-email-domain` succeed and change nothing when the organization doesn't hold the domain; the method used to raise `RobotoNotFoundException`, and the command used to exit with an error. `Org.bind_email_domain` and `roboto orgs bind-email-domain` likewise succeed for a domain the organization already holds, where the method used to raise `RobotoConflictException`. When another organization holds the domain, `Org.bind_email_domain` raises `RobotoOrgEmailDomainChangeRefusedException`, a subclass of `RobotoConflictException`.
  - `Org.invite_user` and `OrgInvite.create` raise `RobotoConflictException`, not `RobotoInvalidRequestException`, when the invitee already has a pending invitation to the organization. Code that catches `RobotoInvalidRequestException` for that case should catch `RobotoConflictException` instead.
  - `OrgInvite.accept` raises `RobotoConflictException` for an invitation that was declined or revoked, `OrgInvite.decline` raises it for one that was accepted, and both raise `RobotoExpiredException` for an expired invitation. Both methods used to raise `RobotoNotFoundException` once an invitation was answered. Declining an invitation you already declined succeeds and changes nothing, and so does accepting an invitation you already accepted, if Roboto has finished setting up the invitation's organization.
  - `OrgInvite.accept` raises `RobotoUnauthorizedException` when Roboto hasn't verified your account's email address. Sign in to the Roboto web app and accept the invitation there instead.
  - `OrgInvite.accept` raises `RobotoServiceUnavailableException` when Roboto hasn't finished setting up the invitation's organization: you're a member of the organization, but you can't work in it until its setup finishes. Call `OrgInvite.accept` again in a few minutes. If the organization still isn't set up, contact the administrator that the exception's message names.
  - `Org.invite_user` and `OrgInvite.create` raise `RobotoLimitExceededException` when the organization's members and pending invitations already reach its member limit. An invitation stops counting toward the limit once it is accepted, declined, or revoked, or once it expires.
  - A View's display states its sort as one field, `ViewDisplay.sort`, in place of `sort_by`, `sort_direction` and `unsorted`. It is a `DefaultSort` (the table's usual order), a `NoSort` (no order at all) or a `ColumnSort` with `by` and `direction`; import all three, and the `ViewSort` union, from `roboto.domain.views`. A `ViewDefinition` is now `view_v2` (`VIEW_SCHEME_V2`); one saved as `view_v1` is read as `view_v2`, and a `ViewDisplay` built with the three older keyword arguments still folds them into `sort`. Reading `display.sort_by`, `display.sort_direction` or `display.unsorted` no longer works.
  - From API version 2026-11-19, `GET` and `PUT` on `/v1/datasets/<dataset_id>/access`, `/v1/collections/<collection_id>/access` and `/v1/views/id/<view_id>/access` describe who a record is shared with as a `RecordAccessResponse`, such as `{"restricted": false, "grants": [{"subject": {"kind": "user", "id": "ben@example.com"}, "role": "viewer"}]}`, and a `PUT` takes an `EditRecordAccessRequest`, such as `{"add": [...], "remove": [...], "restricted": true}`. The response no longer lists the record's owner, a View's author or a dataset's collections. A REST request that sends no `X-Roboto-Api-Version` header is served at the latest API version, so it receives the new shape, and a `PUT` of OpenFGA tuples without the header is refused with HTTP 400. To keep sending and receiving tuples, send `X-Roboto-Api-Version: 2026-11-05`. `Collection.get_access` and `Collection.edit_access` send that version themselves and work as before.
  - `Org.remove_role_from_user` raises `RobotoInvalidRequestException` when given `OrgRoleName.user`, and `PUT /v1/orgs/id/<org_id>/users/id/<user_id>` returns HTTP 400 when `remove_roles` names `user`: every member holds the user role. Remove the member with `Org.remove_user` instead.

## Features Added
  - `AgentThread.from_id`, `refresh`, `events` and `run` read a long thread in several requests, so a thread too large for one response loads where it used to fail with HTTP 507. `GET /v1/ai/threads/<thread_id>` and `GET /v1/ai/threads/<thread_id>/delta` take `paged=true`. The response then stops at a size Roboto sets and reports `has_more`, a new field of `AgentThreadRecord` and `AgentThreadDelta`; the next delta, requested with the response's `continuation_token`, continues from there. A delta's `status` describes the whole thread, so request deltas until one reports `has_more` as `false` before acting on it. Without `paged`, both routes answer as before.
  - Roboto ships skills of its own, which the chat loads without a subscription. They have the new accessibility `SkillAccessibility.Roboto`: every member of an organization a Roboto skill is released to can read it, and nobody can edit, delete, subscribe to or pin one, so those calls raise `RobotoUnauthorizedException`. `Skill.list_for_org()` includes them, `Skill.list_for_org(scope=SkillListScope.Roboto)` lists only them, and `Skill.from_id` and `Skill.from_name` read one. A Roboto skill can carry resources, such as the chapters of a guide: `SkillVersionRecord.resources` lists each by its `slug` and `when_to_use`, a line saying when the chat reads it. Roboto never returns the text the AI reads: the `body` of a Roboto skill's version is empty, and a resource is listed without its text. `Skill.create` and `Skill.update_metadata` refuse `SkillAccessibility.Roboto`: the request fails validation. Roboto skills are served from API version 2026-11-20; for a client that sends an older `X-Roboto-Api-Version`, listings leave them out and reading one answers 404.
  - `Org.create` takes an optional `idempotency_key`, and calling it again with the same key returns the organization the first call created. When you pass no key, the SDK generates one, so its automatic retries never create a second organization. `POST /v1/orgs` accepts the key in an `Idempotency-Key` header.
  - `Org.create` raises `RobotoOrgCreationRefusedException` when your Roboto deployment doesn't let you create an organization. The exception's `next_step` says what to do instead.
  - Organizations can verify the email domains they hold: `Org.start_email_domain_verification` returns a DNS TXT record to publish, `Org.check_email_domain_verification` looks for the record and verifies the domain, `Org.new_email_domain_verification_record` replaces the record, `Org.set_email_domain_auto_join` turns auto-join on or off, and `Org.email_domain_listing` lists the organization's domains and verifications. Where your Roboto deployment requires verification, a person who signs up with an address at a domain joins its organization only while auto-join is on and the domain is verified or Roboto has provisionally approved it; `Org.create(bind_email_domain=True)` starts a verification and includes the TXT record in the `UserWarning` it issues. A refused change raises `RobotoOrgEmailDomainChangeRefusedException`, whose `reason` says why.
  - `Org.invite_user` and `OrgInvite.create` take a keyword argument `role` (default `OrgRoleName.user`) that sets the organization role the invitee receives on accepting, and only an organization owner can send an invite with the `admin` role. `OrgInvite` and `OrgInviteRecord` gain `role`, `status` (an `OrgInviteStatus` of `pending`, `accepted`, `declined`, `revoked`, or `expired`), and `expires_at`, and `OrgInviteRecord` also gains `latest_email_bounced`, which reports whether the latest email sent for the invite bounced. An invite can be accepted only while its status is `pending`, and it expires 14 days after it is sent or an organization admin last renews it.
  - Setting `HttpLoggingOptions.log_only_method_and_origin` to `True` keeps each request's URL path and query, its headers, and its body out of an `HttpClient`'s debug logs and out of the `ConnectionRefusedError` that the client raises; use it for a client whose requests carry secrets or personal data, such as a Slack incoming webhook's URL. It defaults to `False`.
  - `roboto setup --choose-endpoint` and `roboto auth login --choose-endpoint` ask for the Roboto API endpoint to sign in to, offering `https://api.roboto.ai`. Use them when your organization runs its own Roboto deployment. When `roboto setup --choose-endpoint` finds a profile saved for another endpoint, it offers a sign-in that replaces the profile's token and endpoint.
  - `RobotoCredentials.send_requests_to`: storage credentials that the platform issues can name a URL that receives their requests in place of S3. The SDK still signs each request for S3, then sends it to that URL followed by the host and path that the request was signed for. The field is None for most credentials, and then requests go to S3 as before.
  - Embeddings (experimental): `roboto.experimental.embeddings.EmbeddingSpace` lets a producer, such as an action, write its own embeddings to Roboto, and lets anyone read them back. `EmbeddingSpace.register` registers a space by its spec, from which Roboto derives the space's id (registering the same spec again returns the same space, and registering it with another name, display or row shape raises `RobotoConflictException`), and `put_rows` writes a pyarrow Table, pandas DataFrame or Parquet file of window, event or session rows: it sends them in batches of at most 50,000 rows that keep each session's rows together, waits for Roboto to write them, and raises `RobotoEmbeddingBatchRejectedException`, listing the problems, when Roboto rejects a batch. For each session and level the rows carry, they replace what the session held; `replace_levels` names, per session, levels the rows replace in full, so a level the rows carry nothing of for that session, such as its event rows once its events are deleted, ends up empty. `put_rows` also records each session's `inputs_hash`, or why it produced no rows (`no_rows_reason`), which `coverage` and `EmbeddingSpace.coverage_of` read back so a later run can embed only stale sessions. To read what spaces hold, `get_rows` pages through a space's rows (with their vectors and label columns such as `event_name` or `custom.<field>` when asked), `read_rows` takes every option of `EmbeddingRowsRequest` (each row's distance to a seed, a 2-D projection, a stable sample), `EmbeddingSpace.find_similar` ranks the spans most like a seed across spaces, and `EmbeddingSpace.find_anomalies` scores unusual time regions or ranks sessions or events against each other; their requests and answers are in `roboto.experimental.embeddings.search`. An action's token may call them when its grants cover what the request reads: `embedding:read` and `session:read`, plus `event:read` for a similarity search or a read of events, and `custom_field:read` for a request that names a custom field. `from_id`, `list`, `update`, `retire` and `reference_rows` (the space's fleet reference sample, vectors included) complete the API. Writing rows needs the `analytics` extra. The API lives in `roboto.experimental` while its shape settles. Contact Roboto to enable embeddings for your organization.
  - `Collection.get_record_access` returns who a collection is shared with, as a `RecordAccessResponse`: whether it is restricted, meaning that members of its organization need a grant to reach it, and its grants. `Collection.edit_record_access(add=..., remove=..., restricted=...)` adds and removes grants and restricts or unrestricts the collection, and returns the same. A grant is an `AccessGrant` of an `AccessSubject` (`AccessSubject.user`, `.group`, `.org_members` or `.everyone`) and an `AccessRole` (`viewer`, `editor` or `deleter`); import them, `AccessSubjectKind` and `EditRecordAccessRequest` from `roboto.auth`. A grant to `org_members` may name only the collection's own organization, and `everyone` may hold only `viewer`. A call that breaks either rule, or sends a `user`, `group` or `org_members` subject without an ID or an `everyone` subject with one, raises `RobotoInvalidRequestException` naming the grant.
  - `Collection.get_access`, `Collection.edit_access`, `AuthZTupleRecord`, `EditAccessRequest` and `GetAccessResponse` are deprecated. The two methods issue a `DeprecationWarning`. Use `Collection.get_record_access` and `Collection.edit_record_access`, and `AccessGrant`, `EditRecordAccessRequest` and `RecordAccessResponse`, which take and return the shape of API version 2026-11-19.
  - `OrgRecord` gains `access_control_features`, which says whether Roboto has turned on groups, restricted records and organization-defined roles for the organization. Only Roboto staff can change it, and it is `False` until they do. Older SDK releases ignore the field.
  - An organization's admins can make groups of its members, which its records can be shared with. `GET` and `POST` on `/v1/orgs/id/<org_id>/groups` list the organization's groups and make one from a `CreateOrgGroupRequest` (a `name`, unique within the organization whatever its case, and an optional `description`); `GET`, `PUT` and `DELETE` on `/v1/orgs/id/<org_id>/groups/<group_id>` read one, rename it or change its description (`UpdateOrgGroupRequest`), and delete it with its memberships and every share that names it; `GET` and `PUT` on `/v1/orgs/id/<org_id>/groups/<group_id>/members` list its members and add and remove them (`UpdateOrgGroupMembersRequest`; each added user must be a member of the organization). A group is an `OrgGroupRecord`, whose `role_ids` lists the roles it holds where roles apply (see the roles entry below) and is `None` elsewhere, and a member an `OrgGroupMemberRecord`, both in `roboto.domain.orgs`. Any member of the organization can list its groups and their members; only its admins and owners can make, change or delete one. Making a group, renaming it and changing its members return HTTP 400 on a Roboto deployment that does not decide access from Roboto's own tables alone, and otherwise HTTP 401 unless the organization has `access_control_features`; listing and deleting always work. An organization has at most 250 groups (HTTP 400 past that). A record shared with a group is open to its members as the share's role allows. A person removed from the organization, or who leaves it, is taken out of its groups. There is no SDK class or CLI command for groups.
  - Every member of an organization holds exactly one built-in role, `OrgBuiltInRole` in `roboto.domain.orgs`: guest, member, admin or owner, each allowing everything the one before it allows. A guest may do only what every member always may, such as reading the organization, its members, groups and roles, plus what their roles, their groups' roles and records shared with them allow. A guest never invites people or changes the organization's members, groups, roles or settings. Guests exist only on a Roboto deployment that decides access from Roboto's own tables alone, in an organization with `access_control_features`; everywhere else every member is a member, admin or owner.
  - An organization's admins can define roles, each a set of switches such as `view_data`, `upload_data` or `annotate`, and any member or group of the organization may hold several, admins and owners included. Roles only add: a member may do what their built-in role allows plus what the switches of every role they hold, themselves or through a group, turn on. Every switch gives only what a member already has, so roles change what a guest may do and nothing for a member, admin or owner. Two presets, Read-only member (`view_data`, `use_ai`) and Data collector (`view_data`, `upload_data`, `edit_data`, `annotate`, `build_views`), can be held in every organization and cannot be changed or deleted. `GET` and `POST` on `/v1/orgs/id/<org_id>/roles` list the four built-in roles, the presets and the organization's roles (`OrgRoleRecord`, whose `kind` says which) and define one from a `CreateOrgRoleRequest` (a `name`, unique within the organization whatever its case, an optional `description`, and its `switches`); an organization defines at most 250 (HTTP 400 past that). `PUT` and `DELETE` on `/v1/orgs/id/<org_id>/roles/<role_id>` change a role the organization defined (`UpdateOrgRoleRequest`) and delete it, which returns HTTP 409 while anyone holds it; a built-in role or a preset cannot be changed or deleted (HTTP 400). There is no SDK class or CLI command for roles.
  - An organization's admins and owners give roles and make guests. `PUT /v1/orgs/id/<org_id>/users/id/<user_id>/roles` with a `SetOrgMemberRolesRequest` sets a member's built-in role to guest or member and replaces the roles they hold themselves, in one change, and returns their `OrgUserRecord`. `PUT /v1/orgs/id/<org_id>/groups/<group_id>/roles` with a `SetOrgGroupRolesRequest` replaces the roles a group holds and returns its `OrgGroupRecord`. Each request names at most 25 roles (`MAX_ROLES_HELD_DIRECTLY`). Only the organization's admins and owners may define, change, delete or give roles (HTTP 401 for anyone else). An admin, an owner or a service user cannot be made a guest, a user who is not a member cannot be given roles (HTTP 400), and a role ID that is neither a preset nor the organization's returns HTTP 404. Admins and owners are made and unmade through the existing membership update; a guest made an admin or owner there stops being a guest. An invite can also name the built-in role: `CreateOrgInviteRequest.built_in_role` set to `guest` (only with the user role) makes the person a guest when they accept, and `OrgInviteRecord.built_in_role` shows it. Defining, changing and giving roles, making a guest and inviting one return HTTP 400 on a Roboto deployment that does not decide access from Roboto's own tables alone, and otherwise HTTP 401 unless the organization has `access_control_features`; listing and deleting roles always work. A person removed from the organization, or who leaves it, holds none of its roles and is no guest there if they rejoin, and deleting a group takes the roles it held.
  - Every `OrgUserRecord` carries `built_in_role`, which reads `guest` only on a Roboto deployment that decides access from Roboto's own tables alone, in an organization with `access_control_features`. There, the organization's members list also fills `held_roles`: each role the member holds, once, with every way they hold it (`OrgHeldRoleRecord`, whose `through` lists `OrgRoleHeldDirectly` and `OrgRoleHeldThroughGroup` entries). `held_roles` is `None` everywhere else, `roles` reads `["user"]` for a guest and a member alike, and older SDK releases ignore the new fields.
  - An organization's admins can have every new dataset start restricted, by storing `true` under the organization config key `org_new_datasets_start_restricted` (`PUT /v1/config/org/<org_id>/key/org_new_datasets_start_restricted` with `{"value": true}`). Turning it on returns HTTP 400 on a Roboto deployment that does not decide access from Roboto's own tables alone, and otherwise HTTP 401 unless the organization has `access_control_features`; turning it off always succeeds. While it is on, a new dataset is reachable by the organization's members only through a share, and its admins and owners keep access. The user who creates it is shared it as a `deleter`: the person, for a device's token the organization's devices service user, and for an action invocation's token the user the invocation acts as (the person who started it, or the organization's actions service user for a triggered invocation). A dataset created by anything else, such as the Foxglove import, is shared with no one. A triggered invocation is refused a dataset a person created while the setting is on, unless the dataset is shared with the actions service user.
  - A visualizer layout can be shared with named people and groups of its organization. `GET /v1/layouts/id/<layout_id>/access` returns who it is shared with, as a `RecordAccessResponse`: whether it is restricted, meaning personal, so that only its creator, the people and groups it is shared with, the organization's admins and owners, and Roboto staff open it, and its grants. `PUT` on the same route takes an `EditRecordAccessRequest` of grants to add and remove and `restricted`, and returns the same. A `viewer` opens the layout and an `editor` also changes it; neither renames nor deletes it, and a `deleter` grant returns HTTP 400. Setting `restricted` makes the layout personal or shared with the whole organization, as its `accessibility` does, and only its creator and the organization's admins and owners may set it; adding or removing a grant takes permission to change the layout. Layouts shared with the caller, directly or through a group, are listed by `GET /v1/layouts` and opened by `GET /v1/layouts/id/<layout_id>`. A grant returns HTTP 400 on a Roboto deployment that does not decide access from Roboto's own tables, and a grant to a group returns HTTP 401 on one that decides from them alone unless the organization has `access_control_features`. There is no SDK method for a layout's access.

## Behavior Changes
  - `PUT /v1/layouts/id/<layout_id>` changes a layout's `accessibility` only for its creator and the organization's admins and owners (`layout:share`, which a credential granted `layout:update` or `workspace:update` holds), and changes the rest for a person the layout is shared with as an `editor` too. Who may see, change, rename and delete a layout is otherwise unchanged, and a personal layout created before this release is still seen only by its creator, the organization's admins and owners, and Roboto staff.
  - On a Roboto deployment that decides access from Roboto's own tables alone, `PUT /v1/views/id/<view_id>/access` returns HTTP 401 and changes nothing when it adds a grant to a group and the View's organization does not have `access_control_features`. Sharing a View with a person, or with everyone in its organization, is unchanged. The members of a group a View is shared with see it in `GET /v1/views` and open it, and a viewer or editor grant gives them what it gives a person.
  - A REST request acts in one organization. When `X-Roboto-Org-Id` and `X-Roboto-Resource-Owner-Id` name different organizations, the request acts in the one `X-Roboto-Resource-Owner-Id` names; when only one of them is set, it acts in that one; when neither is set, it acts in your only organization. A request that sent different organizations in the two headers and acted in the one `X-Roboto-Org-Id` named now acts in the other one, or gets HTTP 401 if you don't belong to it. Only a route that acts in an organization refuses a request whose headers name an organization you don't belong to; other routes ignore the headers. `GET /v1/actions/<name>` and `POST /v1/actions/<name>/invoke` are the exceptions, described in the next entry. Apart from `Action.invoke`, the SDK and CLI send one organization per request, so their behavior is unchanged.
  - `Action.from_name` and `Action.invoke` name the organization that owns the action in `owner_org_id`: a query parameter on `GET /v1/actions/<name>` and a field of `CreateInvocationRequest` on `POST /v1/actions/<name>/invoke`. On those two routes, a request without `owner_org_id`, such as one from an older SDK release, still names the action's owner in `X-Roboto-Resource-Owner-Id`. That header never chooses the organization the invocation is created in: the invocation is created in the organization `X-Roboto-Org-Id` names, or in your only organization.
  - `User.create` with `CreateUserRequest(is_system_user=True)` and `POST /v1/users` with `"is_system_user": true` raise `RobotoUnauthorizedException` (HTTP 401) for every caller except Roboto's own platform role, and create no user. A Roboto staff member's personal access token or web sign-in used to be enough.
  - Only the person who started an AI thread can advance it. `AgentThread.send`, `AgentThread.send_text`, `AgentThread.submit_client_tool_results`, `AgentThread.run`, and the routes `POST /v1/ai/threads/<thread_id>/messages`, `/retry`, `/tool-results` and `/cancel` raise `RobotoUnauthorizedException` (HTTP 401) for anyone else, including members who can read a thread shared with their organization. Call `AgentThread.fork` to continue in your own copy. Reading and forking a shared thread are unchanged.
  - Creating a webhook integration, replacing its signing secret or provider API key, and deleting it need an admin of the organization: `POST /v1/integrations/webhook/begin`, `PUT /v1/integrations/webhook/id/<webhook_endpoint_id>/signature_secret`, `PUT /v1/integrations/webhook/id/<webhook_endpoint_id>/api_key` and `DELETE /v1/integrations/webhook/id/<webhook_endpoint_id>` return HTTP 401 to other members and change nothing. Any member can still read the organization's webhook integrations.
  - `GET /v1/metering/reports` leaves out the provider-cost meters (`actions::fargate::provider_cost_microdollars` and `actions::microvm::provider_cost_microdollars`) unless you are Roboto staff. Every other meter is returned as before.
  - An expired personal access token or web sign-in token is refused with HTTP 401 on its next request. It used to keep working for up to five minutes after it expired, while the API's cache of its earlier sign-in lasted.
  - Invalid actions fail faster.
  - Device types (`DeviceType`) and the files of devices, device types and orgs (`Device.configurations`, `DeviceType.configurations` and `Org.assets`) are available to every organization.
  - RoboQL no longer offers `schema_version` on topics or `upload_id` on files. Neither field had data behind it, so a query naming either failed with HTTP 500; it is now refused with HTTP 400 naming the field. `msgpaths` on its own is no longer a topics sort field, and `SORT BY msgpaths` is refused with HTTP 400 instead of failing with HTTP 500. Filters such as `msgpaths[cpuload.load].mean > 0` work as before. Older SDK releases see the same responses.
  - `roboto auth login` chooses where to sign in from the config file. With `--profile` (or `ROBOTO_PROFILE`), it signs in at that profile's saved endpoint, so signing in again no longer moves a profile to `https://api.roboto.ai`. With only `--endpoint` (or `ROBOTO_SERVICE_ENDPOINT`), it saves the token to the profile that already uses that endpoint. With neither, it uses the one endpoint the config file's profiles use. It stops without contacting Roboto when two or more profiles fit. In a terminal, a profile that already has a token asks whether to replace it, save the new token to a new profile, or cancel; outside a terminal, replacing it still requires `--overwrite`.
  - `roboto auth login` and `roboto setup` refuse to sign in at a Roboto API endpoint that is neither HTTPS nor HTTP to `localhost`, `127.0.0.1` or `::1`.
  - An organization's admins can do everything its owners can, except change the organization's own record (`Org.update`) and delete the organization: open, change, share and delete restricted datasets and collections and the files, topics and events in them, and read, change, share and delete other members' private Views and visualizer workspaces. Calls that returned HTTP 401 (`RobotoUnauthorizedException`) to an admin for these now succeed. This takes effect on a Roboto deployment once it decides from Roboto's own authorization tables; until then, only owners can do these things. Who may give, take away or remove a member's role is unchanged.
  - Creating, changing and deleting an event attached to a dataset or file follows that dataset's or file's access, in every organization. `Event.create` and `POST /v1/events/create` need the right to change every dataset or file the event attaches to; `Event.update`, `Event.delete`, `Event.delete_many` and the event's other setters, and `PUT` and `DELETE /v1/events/id/<event_id>` and `POST /v1/events/delete`, need the right to change a dataset or file the event is attached to. On a dataset restricted to the people it is shared with, that is a share with the editor role, or being an admin or owner of its organization; a share with the viewer role no longer lets anyone change its events. A refused request gets HTTP 401 and changes nothing. An event attached to no dataset or file stays changeable by any member of its organization. Declaring a `CreateEventsGoal` on a dataset needs the right to change that dataset as well as to read it.
  - Reading the comments on one record takes reading that record, in every organization. `Comment.for_entity` and `GET /v1/comments/<entity_type>/<entity_id>`, and `Comment.from_id` and `GET /v1/comments/<comment_id>`, need the right to read the dataset, file, collection, action or invocation the comments are on, or to read the organization's triggers for a trigger's comments, besides the right to read the organization's comments. On a dataset restricted to the people it is shared with, that is a share on it, or being an admin or owner of its organization; any other member gets HTTP 401 (`RobotoUnauthorizedException`), also for the comments on a file in that dataset. A token whose grants do not cover reading the record is refused the same way. The AI chat's and the MCP server's `list_comments_on_entity` answer such a member that the record has no comments, and `get_entity` on such a comment answers that it was not found. Comments on a record that no longer exists are returned as before.
  - The organization's comment listings leave out comments on records the caller may not read, in every organization. `Comment.recent_for_org`, `Comment.for_entity_type` and `Comment.for_user`, `GET /v1/comments/recent`, `/v1/comments/type/<entity_type>` and `/v1/comments/user/<user_id>`, and the AI chat's and the MCP server's `search_comments` return only comments on a record the caller may read, as `Comment.for_entity` decides it, and on records that no longer exist. A page with comments left out holds fewer comments than usual, or none, and still carries the token for the next page, so keep requesting pages until the token is None.
  - A collection shows each caller only the datasets and files in it that they may read, in every organization. Read in full mode, a collection lists such a member under `missing`, as it lists an event the caller may not read, and in references mode leaves it out: `Collection.from_id` and `GET /v1/collections/id/<collection_id>`, `Collection.list_all` and `POST /v1/collections/search`, and the collection returned by `Collection.create`, `POST /v1/collections/create` and `PUT /v1/collections/id/<collection_id>`. `Collection.changes` and `GET /v1/collections/id/<collection_id>/changes` leave it out of the resources each change added or removed. The AI chat's and the MCP server's `get_entity`, `list_related` and `get_collection_history` leave it out too. On a dataset restricted to the people it is shared with, a member of its organization with no share on it no longer sees it, or its files, in a collection; an admin or owner of the organization, and a person it is shared with, still do.
  - Reading an action invocation by ID takes reading every dataset it was given, in every organization. `Invocation.from_id`, `Invocation.get_logs` and `Invocation.stream_logs`, and `GET /v1/actions/invocations/<invocation_id>`, `/logs`, `/logs/stream` and `GET /v1/compute/invocations/<invocation_id>/logs`, need the right to read the invocation's data source, each dataset its input selectors name, the dataset of each file and topic it selects by ID, and each dataset a file of a session it selects by ID sits in, besides the right to read the invocation. On a dataset restricted to the people it is shared with, that is a share on it, or being an admin or owner of its organization; any other member gets HTTP 401 (`RobotoUnauthorizedException`). The comments on such an invocation, and the AI chat's and the MCP server's invocation log tools and `get_entity`, follow the same rule; the AI tools answer that the invocation was not found. An invocation given no dataset, or whose inputs were chosen only by name or RoboQL query, stays readable by any member of its organization. The invocation's own credential, which its action and sidecars use, always reads it. Listing invocations (`Invocation.query`) and cancelling one by ID are unchanged.
  - A session follows the datasets its files sit in, in every organization: every request that reads or changes one session by ID needs, besides the right to read or manage the organization's sessions, the right to read every dataset a file of the session sits in to read it, and the right to change every such dataset to change it. Reading covers `Session.from_id` and `GET /v1/sessions/id/<session_id>`, the session's files, topics, topic statistics, devices, ingestion status, AI summary and events, its metric values (`GET /v1/metrics/session/<session_id>/`), its topic partitions and topic data read through it (`POST /v2/topics/partitions/query`, `/read-plan`, `/read-plans-by-schema`), and a session event by ID (`GET /v2/events/id/<event_id>`). Changing covers updating, completing and deleting the session, attaching and detaching devices, adding and removing files, setting its summary or Unix offset or a topic's Unix offset within it, skipping files in its ingestion, publishing and pruning its metric values, and creating, changing and deleting its events. Adding a file to a session (`Session.add_files`, `POST /v1/sessions/id/<session_id>/files`) also needs the right to read that file. On a dataset restricted to the people it is shared with, reading takes a share on it and changing takes a share with the editor role, or being an admin or owner of its organization; any other member gets HTTP 401 (`RobotoUnauthorizedException`) and nothing changes. A session whose files sit only in datasets every member can open, or in no dataset (a file of a device, a device type or the organization), behaves as before. A token whose grants do not cover reading or changing datasets is refused a session that holds a dataset's file. An action invocation given a session by ID is refused at creation unless its creator may read every such dataset. The AI chat and the MCP server answer that such a session, and its events, were not found. Lists and searches of sessions (`GET /v1/sessions/`, `POST /v1/sessions/match`, RoboQL search) and requests that name several sessions at once (`POST /v1/sessions/events/query`, `/events/earliest-starts`, `/devices`, `/ingestion/summaries`, `POST /v2/topics/partitions/sessions/query`, `POST /v1/metrics/query`, `/aggregate`) are unchanged.
  - On a Roboto deployment that decides access from Roboto's own tables, a share that names a group must name a group of the record's organization. `PUT` on `/v1/datasets/<dataset_id>/access`, `/v1/collections/<collection_id>/access` and `/v1/views/id/<view_id>/access`, `Collection.edit_record_access` and `Collection.edit_access` refuse with HTTP 400 (`RobotoInvalidRequestException`) a grant to a group that does not exist or that belongs to another organization, and change nothing; they used to accept any group ID. A group Roboto copied from its earlier authorization store stays accepted, and the shares that name such a group keep working.
  - From API version 2026-11-23, a topic record that `POST /v1/topics`, `GET /v1/topics/id/<topic_id>`, `GET /v1/topics/association/<encoded_association>/name/<url_quoted_topic_name>` or `GET /v1/topics/association/<encoded_association>` returns may hold only the first part of the topic's message paths, when the whole list would not fit in one response. A `Topic` built from such a record fetches the rest, so `Topic.message_paths`, `Topic.record.message_paths` and `Topic.get_message_path` see every message path. A REST caller reads the rest by passing the record's `message_paths_next_token` as `page_token` to `GET /v1/topics/id/<topic_id>/message-paths`, and each page's `next_token` to the next request; only a `null` `next_token` ends the list, not a short page. `message_paths_next_token` is `null` when the record holds every message path. At every API version, `POST /v1/topics` returns only the message paths that fit in one response, and `GET /v1/topics/association/<encoded_association>` may end a page early, with a `next_token`, when its topics would not fit in one response.

## Bugs Fixed
  - `Topic.update` keeps `Topic.message_paths` when the update changes no message path. It used to leave the list empty.
  - `Topic.get_data` and `Topic.get_data_as_df` accept `start_time` and `end_time` for a Parquet topic whose timestamp message path records no unit, such as the Parquet topics that ROS bag ingestion writes. Given either one, they raised `Unable to determine timestamp unit of data in field 'publish_time'`.
  - `Org.invite_user` and `OrgInvite.create` send the invitation to an email address that contains `+`, such as `alex+robots@example.com`, exactly as written.
  - When no organization may bind your email domain, as with `gmail.com` and other public email providers' domains, `Org.create(bind_email_domain=True)` creates the organization without binding the domain and issues a `UserWarning`. The `email_domain_binding_outcome` field of the `POST /v1/orgs` response is `null` when the request did not ask to bind a domain, and otherwise one of `bound`, `deny_listed`, `held_by_another_org`, or `verification_started`. `EmailDomainBindingOutcome` also defines `email_not_proven`, a reserved value that Roboto doesn't return.
  - On Linux, a process is no longer limited to about ten new HTTPS connections per second, whatever its thread count. The limit applied to API requests and to reads of topic data by URL (for example `Topic.get_data`). The SDK re-read the system CA bundle for every connection while holding a lock; it now reads the bundle once per process. The certificates it trusts are unchanged, and `SSL_CERT_FILE` and `SSL_CERT_DIR` work as before. A root certificate installed while a process is running is trusted only by processes started afterward. macOS and Windows behave as before.
  - On macOS, upgrading a Homebrew install with `roboto upgrade` no longer breaks `brew upgrade roboto`. Use `brew upgrade roboto` to get this release. If `brew upgrade roboto` fails with "there is already a Binary", run `rm "$(brew --prefix)/bin/roboto" && brew reinstall --cask roboto-ai/tap/roboto`.
